# 实验一：最小可执行内核

## 引言

本实验基于 RISC\-V 64 位架构，在 QEMU 模拟器上借助 OpenSBI 固件，从零构建并运行一个最小化的 ucore 内核。实验要打通的是"从机器加电到操作系统运行"的最短完整链路：让内核被正确地加载到 0x80200000、从约定的入口点开始执行，并在没有任何现成库支持的环境下完成第一次输出。表面上看，这个内核只会打印一行"\(THU\.CST\) os is loading \.\.\."，但为了这行字，链接脚本、入口汇编、SBI 调用约定、内联汇编与层层封装必须各就各位。

本文围绕实验指导书第一章展开，依次回答四个问题：本章的逻辑线是什么（按什么顺序、围绕哪些功能推进）、每个功能模块是如何工作的、实验内容与 OS 原理课程的知识点如何对应、以及哪些重要的原理内容本章尚未覆盖。最后附上练习一（理解内核入口 kern\_entry）与练习二（GDB 跟踪启动流程）的完整调试记录与答案。

## 章节逻辑线

在学习本章具体内容之前，我们了解了加载 OS 的大致流程：**上电 → 复位地址 ****`0x1000`**** 的 ROM 引导代码 → OpenSBI 固件（****`0x80000000`****）→ 内核入口（****`0x80200000`****）**。但这条链只回答了“**谁在加载**”，还没有回答“**具体是怎么实现的**”——固件凭什么知道该把内核放在哪里？内核的第一条指令凭什么恰好出现在 `0x80200000`？一个刚刚被加载进来的内核，连 `printf` 都没有，又是怎么活下来的？

本章深入每一个环节的核心，围绕一个核心问题展开：**“操作系统无法自己加载自己，那么如何把它加载到内存并运行起来？”** 全章按照提出问题的模式逐层推进：

### 1\.1 谁来做加载者？

OS 不能自己加载自己，因此必须有一个先于 OS 运行的程序——bootloader，它完成“加载 OS 到内存 \+ 移交控制权”两件事。bootloader 自身不依赖任何软件环境，只是住在硬件类的存储介质里。固化在硬件中的那一小段，角色是**固件**（x86 上是 BIOS/UEFI，RISC\-V 上是运行在 M 态的 OpenSBI）或**固化引导代码**；它负责把真正住在磁盘上的 bootloader 拉起来。固件运行后，新的问题出现了：它应该把内核加载到哪里、让 CPU 从哪里开始执行？

### 1\.2 加载到哪里、从哪里开始执行？

这需要内核的**内存布局与入口点**预先约定好。通过链接脚本（`tools/kernel.ld`）把 `.text`、`.rodata`、`.data`、`.bss` 各段固定在以 `0x80200000` 为起点的布局，并用 `ENTRY` 指定入口符号 `kern_entry`；链接出的 ELF 再用 `objcopy` 转成更简单的 BIN 镜像，由 QEMU 加载到 `0x80200000`——内核的第一条指令必须恰好位于这个地址。

### 1\.3 入口之后如何“活”起来？

`kern_entry` 只做两件事：设置内核栈（`la sp, bootstacktop`），然后跳入 C 世界的 `kern_init`。但 `kern_init` 里调用 `cprintf`，又引出了同一个鸡生蛋问题：C 标准库的 `printf` 依赖 OS 提供的运行时环境，而我们正在写的恰恰就是操作系统，因此不能直接 `#include <stdio.h>`。

### 1\.4 一无所有如何输出？

解法是从更底层借力：OpenSBI 固件提供“输出一个字符”的原始接口。但内核运行在 S 模式、SBI 服务运行在 M 模式，**跨特权级调用**必须通过 `ecall` 指令，并遵循固定调用约定（`a7` 放功能号、`a0`–`a5` 放参数、`a0` 收回返回值）。C 语言无法执行 `ecall`，只能用内联汇编手动完成这一步，再层层封装：`sbi_call` → `cons_putc` → `cputch` → `cputs` → `cprintf`。

### 1\.5 工程化收尾

以上过程涉及编译、链接、转 BIN、启动 QEMU 等多条命令，不想每次手敲，于是用 `make`/`Makefile` 按依赖关系把它们自动串联，最终一条 `make` 命令完成全部工作。

综上，本章的逻辑线是：**加载者是谁 → 内核放在哪、从哪开始 → 入口做什么 → 无库环境下如何获得 I/O 能力 → 如何工程化构建**，最终回答了开篇的问题：由固件加载内核，内核从约定的入口点接管机器。

## 核心功能实现

本章代码按“自底向上、层层封装”的方式组织，上层模块只依赖下层。我们从顶层逐渐向下层解析，尝试理解完整的调用过程。

### 2\.1 链接、入口与内核初始化

#### 2\.1\.1 链接脚本：`tools/kernel.ld`

在这个脚本中，我们指定了文件的指令集架构、程序的入口函数以及基址，并对各段进行排布。这个脚本规定了内核的加载信息，说明内核的加载地址在哪里，内存是如何排布的。如果链接脚本出现问题，内核就无法开始执行。

#### 2\.1\.2 入口函数：`kern/init/entry.S`

在链接脚本中 `ENTRY(kern_entry)` 指定了入口函数，其实只有两行：

```Plain Text
la sp, bootstacktop
tail kern_init
```

第一行圈出内核栈，`sp` 寄存器指向栈顶；第二行跳转到内核初始化函数，并无法跳回。C 代码依赖栈，但是我们没有任何系统可以为内存准备栈，因此我们需要自己圈，又因为这个架构栈是从高到低增长的，因此 `sp` 指向栈顶。

#### 2\.1\.3 内核初始化函数：`kern/init/init.c`

内核初始第一件事就是自己 `memset`，清空 `.bss` 区，然后 `cprintf` 打印信息完成第一次交互。代码很简短，重要的是我们现在所有的函数都是内核入口亲手完成的而不是依靠成熟的库自动完成的。

### 2\.2 从 SBI 到 `stdio`

在内核初始化时存在一个函数调用 `cprintf()` 完成第一次交互，但是显然这个函数也需要进行定义。这里又遇到了同一个鸡生蛋问题：C 标准库的 `printf` 依赖操作系统提供的运行时环境，而我们正在写的恰恰就是操作系统——`#include <stdio.h>` 在这里是逻辑不通的。出路只有一条：从比内核更低的地方借力。OpenSBI 固件运行在 M 模式，提供“输出一个字符”的原始接口，本节就是从它出发，一层层封装出 `cprintf` 的全过程。

#### 2\.2\.1 SBI 调用函数与封装：`libs/sbi.c` \+ `kern/driver/console.c`

这是内核与固件之间的唯一通道，通过内联汇编和 `ecall` 的调用约定完成从内核调用 SBI 接口的功能。

具体来说，调用约定规定了三个动作：调用前，把功能号放入 `a7` 寄存器、参数放入 `a0`–`a2`；执行 `ecall`，CPU 立即从 S 模式陷入 M 模式，完成提升权限，由 OpenSBI 读 `a7` 得知请求的是哪一号服务，读 `a0`–`a2` 拿到参数；处理完毕后，固件把返回值写回 `a0`，退回 S 模式，内核从 `a0` 取回结果。`sbi.c` 中的 `sbi_call` 函数就是这套约定的完整实现。需要内联汇编的原因在于：C 语言无法表达“触发一次陷入”，也无法指定某个变量必须装进某个寄存器，这两个动作只能手写汇编交给编译器原样保留。

此外还要借助 `console.c` 这个薄层把能力包装成“控制台”：`cons_putc` 只做一件事——把收到的字符转交给 `sbi_console_putchar`。

#### 2\.2\.2 格式化输出：`kern/libs/stdio.c` \+ `libs/printfmt.c`

这是封装链的最上层，负责把“输出一个字符”这个原始能力，逐步搭成“输出格式化字符串”的完整功能。

完整的封装链如下：

```Plain Text
cprintf → cputs → cputch → cons_putc → sbi_console_putchar → sbi_call → ecall → OpenSBI
```

这就是 `kern_init` 里一行 `cprintf` 的完整下行路径：`cprintf` 把格式化任务交给 `cputs`，`cputs` 逐字符调用 `cputch`，`cputch` 经 `cons_putc` 进入控制台层，再经 `sbi_console_putchar`、终由 `sbi_call` 执行 `ecall` 陷入固件，字符才真正出现在屏幕上。其中 `stdio.c` 提供 `cputch`、`cputs`、`cprintf` 三个逐层向上的入口。`printfmt.c` 负责解析 `%d`、`%s` 等格式说明符，将变量转化为字符串。

综上，本章的代码围绕两条主线展开：**第一条主线解决“内核如何被正确加载并跑起来”**——链接脚本规定布局与基址，入口汇编搭好 C 运行所需的最小环境，内核初始化函数接管一切；**第二条主线解决“一无所有如何获得输出能力”**——从固件的原始字符接口出发，经 SBI 调用约定、控制台边界层、格式化封装，最终汇聚成一次 `cprintf`。

## 重要知识点

### 3\.1 RISC\-V 特权级（M/S/U）与 CPU 保护环

- **含义**：特权级是 CPU 对指令权限的分档，RISC\-V 分 M/S/U 三档，分别对应固件/内核/用户程序；x86 有 0–3 环，本质相同。

- **关系**：都是硬件级的权限隔离机制，操作系统的“用户态/内核态分离”正是建立在它之上。

- **差异**：x86 的四环实际主要用两环，RISC\-V 三档职责划分更明确，且跨级跳转统一通过 trap（`ecall`/中断）实现，模型更简洁。

### 3\.2 链接脚本与内存布局 ↔ 程序的链接与装载

- **含义**：链接脚本规定各段（`.text`/`.rodata`/`.data`/`.bss`）在内存中的排布和入口地址；原理课中对应符号解析、重定位与装载——把程序放入内存并建立运行环境。

- **关系**：本实验做的是“链接与装载”的一个特例：没有操作系统帮忙，内核必须用链接脚本亲手规定自己的布局，再靠固件按约定加载。

- **差异**：原理课讨论有 OS 时的通用情形（虚拟地址、动态链接、装载器）；本实验是物理地址、单一固定布局、静态链接的最简情形。

### 3\.3 `.bss` 段手动清零 ↔ 装载器对进程映像的初始化

- **含义**：`.bss` 段在可执行文件里只记录大小、不存数据，运行时须保证为全 0；原理课中这项工作由装载器（如 `exec` 系列调用）完成。

- **关系**：职责完全相同——保证“未初始化”的全局变量真正为零。

- **差异**：有 OS 时由装载器代劳、用户无感知；本实验没有装载器，只能由内核入口亲手调用 `memset`，同一件事的责任主体发生了转移。

### 3\.4 内核栈的设置 ↔ 运行时栈与上下文

- **含义**：`entry.S` 用 `la sp, bootstacktop` 给内核建立初始栈；原理课中栈支撑过程调用、局部变量，也是进程上下文的组成部分。

- **关系**：同一个栈机制，本实验也实证了“栈由高地址向低地址生长”这一约定。

- **差异**：原理课关心栈在进程切换时的保存与恢复；本实验只完成“从零搭出第一个栈”，还没有进程概念，谈不上切换。

## OS 原理中重要、但本实验未涉及的知识点

本实验的任务边界是“从加电到内核能输出一行字”，因此操作系统的许多核心机制尚未登场。以下按重要性列出我认为最关键的五项：

### 4\.1 进程与调度

进程是操作系统 most 核心的概念（进程状态、上下文切换、调度算法）。本实验的内核进入 `while (1)` 后就停在唯一的执行流里，没有进程、没有切换、没有调度——CPU 永远只为这一个“大循环”服务。这也是后续章节最紧要补上的一块。

### 4\.2 虚拟内存与地址转换

页表、MMU、地址翻译、分页机制。本实验只有物理地址上的固定布局，没有页表、没有 `satp`、没有地址翻译，“虚拟”二字尚未出现——内核直接运行在物理地址上。

### 4\.3 中断与异常的完整处理

本实验只体验了“主动陷入”（`ecall`）这一种 trap 的触发，没有中断向量表、没有外部中断（如时钟中断）、没有 trap 的分发与恢复流程——“被硬件打断”这件事还没有发生。

### 4\.4 并发与同步

锁、信号量、互斥。单执行流的最简环境下完全用不到，但这是多进程/多核操作系统的必答题，也是死锁等问题的来源。

## 练习答案与调试记录

### 练习 1：阅读内核入口代码

入口代码如下：

```Plain Text
#include <mmu.h>
#include <memlayout.h>

.section .text,"ax",%progbits
.globl kern_entry
kern_entry:
    la sp, bootstacktop
    tail kern_init

.section .data
.align PGSHIFT
.global bootstack
bootstack:
    .space KSTACKSIZE
.global bootstacktop
bootstacktop:
```

`la sp, bootstacktop` 完成的操作是将栈顶地址放进 `sp` 寄存器里面；`tail kern_init` 是跳转到 `kern_init`。由于 RISC\-V 栈从高地址向低地址增长，因此 `sp` 初始化为 `bootstacktop`，为后续 C 语言函数调用建立栈环境。

### 练习 2：上电

上电流程为：**上电 → 复位地址 ****`0x1000`**** 的 MROM → OpenSBI（****`0x80000000`****）→ 内核入口（****`0x80200000`****）**。

#### 5\.2\.1 初始指令位置与主要功能

RISC\-V 硬件加电后，CPU 从复位地址 `0x1000` 开始执行。最初几条指令位于 `0x1000`、`0x1004`、`0x1008`、`0x100c`、`0x1010`，随后在 `0x1014` 执行跳转。

这些指令位于 QEMU `virt` 机器的 MROM 中，不负责完整的硬件初始化，只完成**最简引导**：准备 `hartid`（`a0`）与设备树地址（`a2`）等参数，从 ROM 槽位读出固件入口 `0x80000000` 并跳转，将控制权移交给 OpenSBI。真正的固件初始化由 OpenSBI 完成；本实验环境下内核镜像由 QEMU 在启动前预加载至 `0x80200000`。

#### 5\.2\.2 调试过程

终端 A 运行 QEMU，使其在启动时暂停并开放 GDB 端口：

```Bash
qemu-system-riscv64 -nographic -machine virt -m 128M -kernel bin/kernel -bios default -s -S
```

终端 B 启动 GDB：

```Bash
riscv64-unknown-elf-gdb bin/kernel
```

连接 QEMU 并查看初始指令：

```Plain Text
target remote :1234
info registers pc
x/5i $pc
si
```

连接后，`info registers pc` 确认：

```Plain Text
pc             0x1000   0x1000
```

使用 `x/5i $pc` 观察到：

```Plain Text
0x1000:      auipc   t0,0x0
0x1004:      addi    a2,t0,40
0x1008:      csrr    a0,mhartid
0x100c:      ld      a1,32(t0)
0x1010:      ld      t0,24(t0)
```

随后使用 `si` 单步执行，观察到 PC 从 `0x1000` 依次经过 `0x1004`、`0x1008`、`0x100c`、`0x1010` 和 `0x1014`，最后跳到 `0x80000000`，进入 OpenSBI。

尝试使用以下命令观察内核加载瞬间：

```Plain Text
watch *0x80200000
c
```

但该观察点始终未触发。作为替代，在复位阶段直接查看内核地址：

```Plain Text
x/5i 0x80200000
```

结果显示内核指令已经位于内存中，说明当前环境下 QEMU 在启动前就将内核镜像预加载到了 `0x80200000`，不存在运行过程中把内核写入该地址的加载瞬间。

重新启动后，先设置内核入口断点：

```Plain Text
b *0x80200000
c
x/5i $pc
si
si
```

断点正确设置在 `kern/init/entry.S:7`，并命中 `kern_entry`。命中后，`x/5i $pc` 显示：

```Plain Text
0x80200000 <kern_entry>:     auipc   sp,0x3
0x80200004 <kern_entry+4>:   mv      sp,sp
0x80200008 <kern_entry+8>:   j       0x8020000a <kern_init>
0x8020000a <kern_init>:      auipc   a0,0x3
0x8020000e <kern_init+4>:    addi    a0,a0,-2
```

这说明 `la sp, bootstacktop` 被展开为 `auipc` 和 `mv` 等真实指令，`tail kern_init` 被编译为一条 `j` 跳转指令。继续使用 `si` 单步，可以观察到设置栈指针后跳入 C 语言函数 `kern_init`。

#### 5\.2\.3 观察结果

1. **初始指令位置**：加电后第一条指令位于复位地址 `0x1000`，属于 QEMU `virt` 机器的 MROM，GDB 无法对应源码。

2. **初始指令功能**：这些指令完成最简引导——准备 `hartid`（`a0`）、设备树地址（`a2`）等参数，从 ROM 槽位读出固件入口 `0x80000000` 并通过 `jr` 跳转，将控制权移交给 OpenSBI，自身不做完整的硬件初始化。

3. **固件阶段**：OpenSBI banner 显示 `Firmware Base: 0x80000000`、`Domain0 Next Address: 0x80200000`、`Next Mode: S-mode`，即固件完成初始化后以 S 模式跳转到 `0x80200000`，将控制权交给内核。

4. **加载时机**：`watch` 未触发，而在 `0x1000` 阶段即可读出 `0x80200000` 处的内核指令，说明本环境下内核镜像由 QEMU 在启动前预加载。

5. **交接确认**：断点精确命中 `kern_entry`（`entry.S` 第 7 行），单步可以看到设置栈指针后通过 `tail` 跳入 `kern_init`，启动流程跟踪到此闭环。
