# Lab3 实验报告：断，都可以断

## 一、实验目的与内容

本实验在 Lab2 的物理内存管理与页表机制基础上，引入 RISC-V 中断和异常处理机制，使内核能够响应运行过程中出现的硬件事件与程序异常。学习重点包括 RISC-V 的特权级与 Trap 路由、相关控制状态寄存器、上下文保存与恢复、汇编入口与 C 语言处理程序之间的衔接，以及时钟中断和临界区保护。

本报告依据实验指导书与实验框架说明非练习部分的原理和结构。两个编程练习仅保留标题，其实现说明、spec、prompt、AI 生成代码中的 bug 与解决过程均留待实际完成练习后填写。本文中的执行流程描述的是框架设计及完整系统应具备的行为，不作为编译、运行或测试通过的记录。

## 二、对本章节整体逻辑线的理解

本章围绕“外部事件或程序异常如何打断当前程序，并在处理后正确继续执行”展开，按照硬件机制、入口现场、软件分发、事件来源和并发保护的顺序逐步建立完整认识。

首先，区分异步的中断与同步的异常，了解 M、S、U 三种特权级，以及事件通过委托机制进入内核的条件。这一步解决“发生了什么、由谁处理”的问题。

其次，通过 `stvec` 建立统一 Trap 入口，认识处理器自动记录的 `sepc`、`scause`、`stval` 和状态信息。硬件只完成进入处理程序所必需的状态变更，通用寄存器仍然需要软件保存，因此接下来引入 `trapframe`，将被打断执行流的现场组织成汇编和 C 代码都能理解的数据结构。

在此基础上，汇编入口承担现场管理，C 语言层通过 `trap()` 和 `trap_dispatch()` 进行事件分发。处理完成后，再通过统一返回路径恢复现场，并由 `sret` 恢复执行。这构成“进入、保存、处理、恢复、返回”的主线。

随后，以时钟作为能够反复产生事件的硬件来源：初始化时设置第一次事件，运行期间再安排后续事件。这样可以理解内核为何即使停留在空循环中，也能被硬件事件打断。

最后，中断也意味着共享数据可能在操作尚未结束时被另一条执行路径访问，因此本章回到物理内存管理，对分配和释放操作加入中断状态保存与恢复。由此将“响应事件”和“维护内核数据一致性”联系起来。

整体流程可以概括为：

```text
启动内核
  → 建立 Trap 入口
  → 初始化物理内存管理和时钟
  → 开启 S 模式中断
  → 硬件事件到达，处理器进入统一入口
  → 软件保存现场并进入 C 语言处理层
  → 按原因分发处理
  → 恢复现场并执行 sret
  → 原执行流继续运行
```

这里的现场切换只表示暂时进入 Trap 处理路径；本实验尚未据此实现不同进程之间的调度切换。

### 3.2 初始化过程

从 `entry.S` 进入 `kern_init()` 后，内核清零 BSS，初始化控制台并输出内核信息，随后设置 Trap 入口、初始化物理内存管理，再初始化时钟并开启全局中断。本地框架还在清零 BSS 后调用 `dtb_init()`，读取设备树中的内存信息。

`idt_init()` 将 `sscratch` 清零，并将四字节对齐的 `__alltraps` 地址写入 `stvec`。虽然函数名沿用了 IDT 的命名习惯，这里的实际工作是配置 RISC-V 的 Trap 入口寄存器。框架中在 `pmm_init()` 前后各调用了一次 `idt_init()`，两次都设置同一入口。

`clock_init()` 使能时钟这一中断来源、安排首次时钟事件并清零 `ticks`。之后 `intr_enable()` 设置 `sstatus.SIE`，允许当前 S 模式执行流响应已使能的中断。先准备处理入口和必要状态，再开放中断，可以避免事件到来时处理环境尚未就绪。

## 四、中断机制及支撑模块分析

### 4.1 Trap 分类、特权级与委托

RISC-V 中的 Trap 是中断与异常的总称。中断是异步事件，例如定时器到期、设备完成 I/O；异常是当前指令触发的同步事件，例如非法指令、断点、缺页和环境调用。教材中“陷阱”有时专指主动触发的同步异常，阅读时应结合语境区分。

M 模式通常运行 OpenSBI 等底层固件，S 模式运行操作系统内核，U 模式运行用户程序。M 模式通过 `mideleg` 和 `medeleg` 将部分中断或异常交给 S 模式处理。已委托且满足条件的事件可直接进入 S 模式处理程序，无须每次先执行 M 模式处理代码；具体路由取决于事件原因、当前特权级和固件配置。

U 模式执行 `ecall` 可以在相应委托配置下进入 S 模式请求操作系统服务；本实验内核在 S 模式调用 SBI 时，也通过 `ecall` 请求 M 模式固件服务。两者触发的异常原因和服务对象不同。

本实验的实际运行主体是 S 模式内核，因此 Trap 也可能是 S 模式进入 S 模式。不能把每次 Trap 都理解为用户态进入内核态。

### 4.2 关键寄存器及硬件行为

| 寄存器或字段 | 在本实验中的含义 |
| --- | --- |
| `stvec` | 保存 S 模式 Trap 入口基址及入口模式。 |
| `sepc` | 记录返回执行所需的指令地址。 |
| `scause` | 最高位区分中断和异常，其余位给出原因编码。 |
| `stval` | 保存与异常有关的附加信息，其内容取决于异常类型。 |
| `sstatus.SIE` | 控制当前处于 S 模式时，对 S 模式中断的全局使能。 |
| `sstatus.SPIE` | 保存进入 Trap 前的 SIE 状态。 |
| `sstatus.SPP` | 记录进入 S 模式 Trap 前的特权级。 |
| `sie`、`sip` | 分别表示各类 S 模式中断的使能和待处理状态。 |
| `sscratch` | 供内核暂存信息，本框架的保存宏用它暂存原始栈指针。 |

本实验使用 `stvec` 的 Direct 模式，所有交给 S 模式的中断与异常先进入同一个入口。其低两位为模式位，入口地址要求四字节对齐。若使用 Vectored 模式，异步中断可按原因进入不同偏移处，同步异常仍进入基址。

进入 S 模式 Trap 时，硬件记录返回地址、原因和相关附加信息，将原 SIE 保存到 SPIE，并清除 SIE，同时记录原特权级到 SPP，然后转到入口。硬件不会自动把全部通用寄存器压入内存，也不会仅凭进入 S 模式就替软件完成内核栈切换。

SIE 主要控制异步中断的接收，关闭它不能阻止当前指令引发非法指令、访存错误等同步异常。

### 4.3 Trap frame 与已有现场保存机制

`struct trapframe` 是汇编入口与 C 语言处理层共享的现场表示。其中，`pushregs` 按 `x0` 至 `x31` 的顺序排列通用寄存器，随后为 `status`、`epc`、`badvaddr` 和 `cause`。在 RV64 下，共有 36 个 8 字节槽位，总大小为 288 字节。

| 内容 | 相对 Trap frame 起点的字节偏移 |
| --- | --- |
| `x0` 至 `x31` | `0` 至 `248`，步长为 `8` |
| `status` | `256` |
| `epc` | `264` |
| `badvaddr` | `272` |
| `cause` | `280` |

`badvaddr` 是框架沿用的字段名，保存的是现代规范中 `stval` 对应的信息，汇编中可见旧名 `sbadaddr`。

已有的 `SAVE_ALL` 先把进入时的 `sp` 放到 `sscratch`，再向低地址扩展栈，预留整个 Trap frame 的空间。由于扩展后的 `sp` 已改变，`gpr.sp` 槽位需要保存先前暂存的原始值。其他通用寄存器先写入各自槽位，之后才借用部分寄存器读取 CSR，避免覆盖被打断程序的原值。

结构体布局与汇编偏移共同构成接口约定。C 代码能够通过 `tf->status`、`tf->epc` 等字段理解现场，是因为两侧对同一段内存采用了完全一致的布局。

### 4.4 统一入口、分发层与诊断支持

`trap(struct trapframe *tf)` 是 C 语言层的统一入口，继续调用 `trap_dispatch()`。后者将 `cause` 转成同宽有符号整数，利用最高位为 1 时结果为负这一性质，区分中断与异常，再交给对应处理层。

这种组织方式使入口和现场管理可以复用。新增某类事件时，主要扩展对应的处理逻辑，而不必为每一种原因重新设计现场保存结构。

`trap_in_kernel()` 根据保存现场中的 SPP 判断 Trap 是否来自内核。`print_trapframe()` 与 `print_regs()` 输出寄存器、状态、返回地址和原因，便于定位入口错误或未知事件。不过，打印现场本身只提供诊断信息，并不意味着已经排除异常原因或具备恢复执行的条件。

返回阶段使用 `sret`。处理器根据 SPP 选择返回特权级，将 PC 置为 `sepc`，并将 SIE 恢复为 SPIE。返回目标也可以是原来的 S 模式内核。本实验尚未建立完整的用户进程运行环境。

### 4.5 时钟驱动与时间基准

时钟驱动通过 `rdtime` 读取时间计数器，再通过 `sbi_set_timer()` 请求定时事件。虽然本地辅助函数名为 `get_cycles()`，其 RV64 实际指令是 `rdtime`，因此读到的是时间计数器，不应直接当作 CPU 执行周期数；后者对应 `rdcycle`。

`clock_init()` 设置 `sie` 中的时钟使能位，通过 `clock_set_next_event()` 安排首次事件，并初始化 `ticks`。这里配置的是具体中断来源，`intr_enable()` 配置的是 S 模式全局开关，两层控制共同影响当前内核能否响应时钟中断。

框架中的事件间隔为 100000 个时间计数单位。在指导书假定的 QEMU 10 MHz 时间基准下：

```text
事件间隔 = 100000 / 10000000 秒 = 0.01 秒 = 10 毫秒
名义频率 = 100 次/秒
```

这是根据时间计数器频率计算的名义间隔。平台时间基准可能不同，且“当前时间加间隔”的设置方式还会受到处理延迟影响，不能据此断言实际打印时刻严格相隔一秒。

定时接口安排的是一次事件，持续的时钟活动需要软件不断安排后续事件。这体现了硬件提供时间通知、软件组织周期性工作的分工。`ticks` 使用 `volatile`，可避免编译器错误地假定其值不会被异步路径改变，但 `volatile` 本身不提供互斥、复合操作原子性或多核同步。

RV32 读取 64 位时间值时，框架采用“高位、低位、高位”的读取与重试方式，避免低位进位使拼接结果不一致；RV64 则可直接读取完整值。

### 4.6 中断开关与临界区保护

物理页面的分配与释放可能同时涉及空闲链表、页面属性和计数器更新。若中间状态被中断路径观察或修改，可能破坏数据结构的一致性。

`intr_enable()` 与 `intr_disable()` 分别设置和清除 `sstatus.SIE`。`__intr_save()` 先判断原中断状态，如果原来开启就关闭并返回真，否则返回假。`__intr_restore(flag)` 仅在标志为真时重新开启中断。`alloc_pages()` 和 `free_pages()` 使用这一接口，在操作页面管理器前屏蔽中断，并在结束后恢复进入时的状态。

保存原状态可以支持嵌套使用。例如，外层关闭中断后进入内层临界区，内层记录到的是“原本关闭”，因此退出时不会提前开启中断；最终由外层恢复原状态。若退出临界区时无条件开中断，就会破坏这一关系。

`local_intr_save(x)` 使用 `do { ... } while (0)`，将多条语句包装成一条可带分号调用的语句，避免嵌入 `if/else` 时出现语法或控制流问题。循环条件恒为零，因此宏体只执行一次。

本地关闭中断只约束当前 hart 上相应中断的进入，不能阻止其他 hart 同时访问共享内存。`libs/atomic.h` 中的原子位修改则依靠 AMO 指令完成特定内存单元的不可分割更新；单个位更新也不能自动保证整条链表操作或跨多个变量的不变量成立。多核情形还需要锁与适当的内存顺序约束。

## 五、练习

### 功能模块一：Trap 上下文恢复与 Trap 入口功能（设计提示词借助 AI 完成）

#### 1. 功能理解与关键约束

本模块处于 Trap 处理链的两端：入口端在 SAVE_ALL 之后把现场交给 C 语言的 trap()，返回端在 trap() 之后把现场还给被打断的执行流。需要完成的两处代码为 RESTORE_ALL 宏（在 trapentry.S 中定义）与 __alltraps 内标有 "lab3" 的代码空位。

对 RESTORE_ALL 的理解：它不是 SAVE_ALL 的机械逆序，而是受三条硬约束支配的恢复序列，三条约束全部来自 SAVE_ALL 的实际保存关系与栈向低地址生长这一事实。其一，CSR 必须先于通用寄存器恢复：RISC-V 不存在从内存直接装载到 CSR 的通路，恢复 sstatus、sepc、sbadaddr、scause 必须经某个通用寄存器中转，中转动作必然暂时污染该寄存器；若先恢复通用寄存器再做 CSR 中转，刚写回的现场会被破坏。其二，恢复 sp 槽（偏移 2）的装载必须是最后一次以 trapframe 基址为地址的访存：槽 2 保存的是中断前的旧 sp，其值等于 frame 基址加 288，位于 frame 顶端之外；该装载一旦执行，sp 即从 frame 低地址端移到其高地址端之外，frame 内其余槽位从此不可达，因此一切依赖基址的取数必须先于它完成。其三，x0 是硬连线零寄存器，不恢复；同时"恢复 sp 之后无需再执行弹栈 addi"由第二条约束直接推出——槽 2 中保存的正是分配 frame 之前的 sp，装载它本身即完成栈平衡。这一点未在提示词中显式写出，作为检验生成方是否真正理解布局的推导点保留。

对 __alltraps 空位的理解：SAVE_ALL 执行完毕后，sp 恰等于 trapframe 起始地址；按 RISC-V 调用约定将该地址经 a0 传给 trap() 并调用之，trap() 返回后控制流自然落入 __trapret。此段代码对一切 Trap 类型同构，不得内嵌类型相关判断，也不得破坏恢复所需的 frame 内容与栈平衡。

#### 2. Spec 与 Prompt 的形成过程

本节记录模块一提示词从分析到成稿的路径。

第一步，先定位"陷阱密度"，再动笔。拿到模块一的要求后，没有直接让 AI 生成代码，而是先通读指导书与 SAVE_ALL，把功能描述翻译成具体的正确性约束。分析发现，模块一的全部陷阱集中在 RESTORE_ALL 的恢复顺序上，共三条：其一，RISC-V 没有从内存直接装载到 CSR 的通路，恢复 CSR 必须经通用寄存器中转，中转必然暂时污染该寄存器，因此 CSR 写回必须安排在一切通用寄存器恢复之前；其二，槽 2 保存的是分配 frame 之前的旧 sp，恢复 sp 的指令一旦执行，sp 即从 frame 低地址端移到其高地址端之外，frame 内其余槽位从此不可达，因此这条装载必须是最后一次基于 frame 基址的访存；其三，x0 是硬连线零寄存器，无需恢复。这三条不是文档现成给出的，而是从 SAVE_ALL 的保存关系加上"栈向低地址生长"这一事实推出来的——它们构成了后来 spec 的全部素材。为确认第二条约束的真实杀伤力，我们还专门推演过反例：若先恢复 sp 再去取其它槽，新 sp 加偏移指向的是 frame 之外的未知内存，且不存在任何补救指令——这个反例后来被直接写进了 spec 的顺序约束。

第二步，把机制知识翻译成行为规格，绕开两类坏写法。课程规范明确禁止极简指令（只说"实现 RESTORE_ALL"）和伪代码类（逐行规定操作）两种失败写法。我们的取舍标准是：凡是"为什么"很硬的知识，写成不变量；凡是"怎么做"，留给生成方推。两个代表性的例子：CSR 顺序没有写成"先恢复 CSR"，而写成"恢复 CSR 必须经过通用寄存器中转再写回，且全部 CSR 写回必须先于任何通用寄存器恢复完成"——前者是步骤，后者是性质；栈平衡没有写成"恢复完执行 addi sp, sp, 288"，而写成"sp 恢复为 Trap 发生前的栈顶值，恢复完成后栈自然平衡，此后不得再对 frame 区域做任何访存"——要不要 addi、弹多少，由生成方依据布局自行推导。

第三步，有意留一个推导点作为试金石。spec 全文没有出现"不需要 addi 弹栈"。这是刻意保留的：如果显式告诉 AI 这句话，它照做即可，无法区分它是真理解了"槽 2 保存的就是旧 sp"还是死记指令；不告诉它，从生成结果里有没有多余的 addi，就能判断生成方是否真懂布局。后来 AI 的生成结果确实没有 addi，说明规格中的前置状态与后置效果足以约束出唯一正确的落点，这个设计被实际结果验证。

第四步，按四段式框架成稿，但每段都服务于前三步的结论。任务说明段把第一步就确定的边界写死——只允许改 trapentry.S 两处，禁止修改 SAVE_ALL、trapframe 布局、trap() 签名与 __trapret；依赖段只给最小集合（SAVE_ALL 全文、trapframe 布局、riscv.h 的宏、调用约定），并明确"布局以 SAVE_ALL 为准，不得另行假设"，防止生成方凭结构体字段名脑补偏移；接口清单段锁定交付物、禁止新增对外可见符号；行为规格段即第二、三步的产物。措辞上有一处可以说明的推敲：约束 CSR 顺序时，最终选定的表述是"必须先于全部通用寄存器的恢复完成"，而不是字面上更宽泛的"CSR 最先恢复"——前者精确对应"中转污染必须发生在一切恢复之前"这一机制事实，不给实现留出歧义空间。

成稿与验证。提示词一次成稿，生成代码一次通过验收。第 3 节逐段分析可见，生成代码的注释与 spec 的两条顺序约束一一对应，说明规格语言被准确接收；无 addi 的推导点被正确解出，说明行为规格确实传递了布局知识而非指令序列。


#### 3. 对生成代码的理解

生成代码由 RESTORE_ALL 宏与 __alltraps 空位处两段组成，整体如下：

```asm
    #lab3 function1 2411645
    # restore sstatus, sepc, badvaddr and scause first, through the
    # scratch registers s1-s4; they are dirtied by this, so all CSR
    # writes must complete before any general register is restored
    LOAD s1, 32*REGBYTES(sp)
    LOAD s2, 33*REGBYTES(sp)
    LOAD s3, 34*REGBYTES(sp)
    LOAD s4, 35*REGBYTES(sp)
    csrw sstatus, s1
    csrw sepc, s2
    csrw sbadaddr, s3
    csrw scause, s4

    # restore x registers (x0 is hard-wired zero and never written)
    LOAD x1, 1*REGBYTES(sp)
    LOAD x3, 3*REGBYTES(sp)
    LOAD x4, 4*REGBYTES(sp)
    LOAD x5, 5*REGBYTES(sp)
    LOAD x6, 6*REGBYTES(sp)
    LOAD x7, 7*REGBYTES(sp)
    LOAD x8, 8*REGBYTES(sp)
    LOAD x9, 9*REGBYTES(sp)
    LOAD x10, 10*REGBYTES(sp)
    LOAD x11, 11*REGBYTES(sp)
    LOAD x12, 12*REGBYTES(sp)
    LOAD x13, 13*REGBYTES(sp)
    LOAD x14, 14*REGBYTES(sp)
    LOAD x15, 15*REGBYTES(sp)
    LOAD x16, 16*REGBYTES(sp)
    LOAD x17, 17*REGBYTES(sp)
    LOAD x18, 18*REGBYTES(sp)
    LOAD x19, 19*REGBYTES(sp)
    LOAD x20, 20*REGBYTES(sp)
    LOAD x21, 21*REGBYTES(sp)
    LOAD x22, 22*REGBYTES(sp)
    LOAD x23, 23*REGBYTES(sp)
    LOAD x24, 24*REGBYTES(sp)
    LOAD x25, 25*REGBYTES(sp)
    LOAD x26, 26*REGBYTES(sp)
    LOAD x27, 27*REGBYTES(sp)
    LOAD x28, 28*REGBYTES(sp)
    LOAD x29, 29*REGBYTES(sp)
    LOAD x30, 30*REGBYTES(sp)
    LOAD x31, 31*REGBYTES(sp)

    # restore sp (frame slot 2) last: this is the final memory access
    # still addressed off the trap frame base
    LOAD x2, 2*REGBYTES(sp)
    .endm

    .globl __alltraps
    .align(2)
__alltraps:
    SAVE_ALL

    #lab3 function1 YOUR 2411645
    # sp should be the same as before "jal trap"
    # pass the trap frame (current sp) as the tf argument, then call trap;
    # sp is callee-saved, so on return it is unchanged and still equals tf,
    # and the fall-through reaches __trapret
    move a0, sp
    jal trap
```

其一，CSR 恢复段采用四只中转寄存器的批量预取。实现用 s1 至 s4 把槽 32 至 35 一次取齐，再连续执行四个 csrw 写回 sstatus、sepc、sbadaddr 与 scause。这一安排满足规格的顺序约束：全部 CSR 写回都发生在任何通用寄存器恢复之前。由于此刻 s1 至 s4 尚未恢复，保存的还是 SAVE_ALL 阶段使用过的值，被中转弄脏没有后果——紧随其后的通用寄存器段会把 x9 至 x18 从槽 9 至槽 18 正确写回。换言之，这段代码利用了"恢复完成之前一切寄存器值都是临时的"这一窗口，把 CSR 的装载与写回集中放置，在结构上清晰分隔了"借寄存器"与"还寄存器"两个阶段，也避免了单个中转寄存器在装载与写回之间被反复覆盖。

其二，通用寄存器恢复段以升序镜像 SAVE_ALL。实现从槽 1（ra）起，按槽号升序恢复 x1 与 x3 至 x31，并刻意跳过两处：槽 0（x0）是硬连线零寄存器，写回既无必要也不可能改变其值；槽 2（sp）被留到宏的末尾。升序并非规格的强制要求（规格只约束 CSR 先行与 sp 殿后），选择升序使恢复序列与 SAVE_ALL 的保存序列一一镜像，肉眼对照即可逐行核对偏移量的正确性。

其三，sp 的殿后恢复与"没有 addi"是同一事实的两面。全宏最后一条访存是 LOAD x2, 2*REGBYTES(sp)，执行后 sp 取得槽 2 中保存的旧栈顶，恰为 frame 基址加 288；frame 所占的 288 字节随之自然弹出，因此宏内没有、也不应有一句弹栈 addi——槽 2 保存的本就是分配 frame 之前的 sp，恢复它本身即完成栈平衡。若画蛇添足地执行 addi sp, sp, 288，反而会把 sp 推到旧栈顶之上 288 字节处，直接破坏被打断执行流的栈。这一点未在提示词中显式写出，由生成方依据 SAVE_ALL 的保存关系自行推导得出，说明规格中的前置状态与后置效果足以约束出唯一正确的落点，这也是验收时判断生成结果"真理解布局"还是"碰巧正确"的试金石。

其四，__alltraps 空位以两条指令完成汇编到 C 的交接。SAVE_ALL 执行完毕后 sp 即 trapframe 的起始地址，move a0, sp 按 RISC-V 调用约定把 frame 地址送入首参寄存器，jal trap 转入 C 语言处理层。空位之后没有显式跳转：jal 的返回地址恰好落在空位末尾，trap() 返回后控制流自然落入 __trapret。代码注释指出 sp 是被调用者保存寄存器、trap() 返回时其值不变——这是返回路径的隐含前提：RESTORE_ALL 的全部装载都以 sp 为 frame 基址，若 trap() 一方违反调用约定改动 sp，返回后所有恢复操作将基于错误的基址进行，后续 sret 的语义也随之失真。选择 jal 而非 call 伪指令，效果相同而形式更贴近汇编层，call 本身就是 jal ra, 目标地址 的语法糖。

其五，jal 对 ra 的覆盖无害，这一点值得单独说明。jal 会把返回地址写入 ra，表面上与槽 1 保存的原 ra 冲突；实际上 SAVE_ALL 早已把被打断代码的 ra 存入槽 1，jal 写入的仅是寄存器 ra 中的临时值，全程未写回内存，RESTORE_ALL 的 LOAD x1 取出的仍是原 ra。这印证了规格中"不得破坏 frame 内容"的确切含义：需要保护的是内存中的 trapframe，在进入恢复段之前，寄存器层面的临时覆盖无关紧要。

其六，代码注释与规格条款形成一一对应。CSR 段注释"all CSR writes must complete before any general register is restored"与 sp 段注释"this is the final memory access still addressed off the trap frame base"，恰好对应规格中的两条顺序约束。静态审查时可直接以注释为索引核对实现是否越界，审查成本因此显著降低，也符合"边界清晰、要求可验证"的提示词设计目标。

### 功能模块二：中断与异常处理功能（设计提示词借助 AI 完成）

本模块补全 `trap.c` 中的 `interrupt_handler()` 和 `exception_handler()`，负责按照 Trap 原因处理监督态时钟中断、其他已列出的中断、未知中断、非法指令异常、断点异常及其他异常。两个函数接收统一入口保存的 `trapframe`，处理完成后交回既有的 Trap 返回路径；本模块不改写汇编入口、现场恢复或 `sret` 流程。

#### 练习内容与实现说明

`interrupt_handler()` 根据 `tf->cause` 识别中断。由于 RISC-V 原因值最高位表示中断，分类时需要先去掉该标志，再使用剩余位作为中断编号。监督态时钟中断每次都设置下一次时钟事件，并将 `ticks` 增加一次；每累计 100 次输出一次统计信息。正常运行时累计输出十次后调用 SBI 关机接口。其他已列出的中断输出对应类型提示，未知中断则输出原因编号并打印完整 Trap frame。

`exception_handler()` 对非法指令和断点异常输出异常指令地址，并按指令编码长度更新 `tf->epc`，使返回后继续执行下一条指令。判断长度时读取指令起始地址的低 16 位：最低两位为 `11` 表示 32 位指令，返回位置前移 4 字节；否则按本实验支持的 16 位压缩指令处理，前移 2 字节。这样既避免重复执行引发异常的指令，也不会跳过压缩指令后的有效指令。其他异常只打印 Trap frame，不擅自改变返回位置。

#### spec 与 prompt 的编写

两个函数共同完成 Trap 处理、共享现场结构及返回约束，因此按实验指导书建议的功能粒度编写为一份多函数 prompt，而不是拆成缺少上下文的独立片段。

spec 按函数分别列出前置条件、后置条件、处理分支和额外要求。中断处理的前置条件说明 Trap frame 与时钟初始化状态；后置条件规定只有监督态时钟中断修改 `ticks`，且不改写返回现场；不同 Case 分别描述时钟中断、其他已知中断和未知中断。异常处理的前置条件说明异常地址可读及指令对齐要求；后置条件规定非法指令与断点更新 `epc`，其他异常保留现场；不同 Case 覆盖两类需要恢复的异常及其余异常。Requirements 则约束中断标志处理、时钟事件续设、16/32 位指令长度判断，以及处理函数与既有 Trap 返回机制之间的边界。

prompt 的 `[PROMPT]` 写明基础分支、目标文件、实际修改要求和不得改变的范围；`[RELY]` 摘录仓库真实的 IRQ/异常编号、`trapframe` 字段、时钟变量与可调用接口；`[GUARANTEE]` 列出两个必须实现的函数签名；`[SPECIFICATION]` 将 spec 中每个函数的状态约束和处理分支具体化。按此方式组织信息，使代码生成受工程接口约束，也方便用现有评分用例验收。

#### AI 生成代码中的问题与解决

实现过程中的问题处理与代码审查重点如下。分支、原因编号输出和脚本行尾有实际修正记录；异常返回位置属于实现时明确约束并验证的检查项。

1. **项目分支容易选错。** 仓库默认克隆目录停留在 `lab1`，该分支没有本模块所需的 Trap 处理代码。根据实验要求重新克隆并确认 `lab3` 分支及基准提交后，才在相应实验框架中实现和验证，避免将实现建立在不匹配的代码版本上。
2. **未知中断原因的输出可能缩窄。** 首版候选实现把 `uintptr_t` 原因编号转换为 `int` 并使用十进制 `%d` 输出。在 RV64 下，较大的原因值可能因此被截断。复核类型宽度后改用匹配 `unsigned long` 的 `%lu`，保留完整原因编号。
3. **检查异常返回位置与指令长度是否一致。** 固定前移 4 字节可能略过 16 位压缩指令后的下一条指令。因此在 spec 中明确要求读取指令低半字，按照最低两位编码决定前移 2 或 4 字节，并通过额外用例验证。该项没有出现经测试确认的返回故障，不能将其写成已经发生过的 bug。
4. **评分脚本受到 Windows 行尾影响。** 早期工作副本中的 shell 脚本带有 CRLF，Linux Shell 因回车符报错。新建 `lab3` 工作副本时设置 `core.autocrlf=false`，确认评分脚本不含 CR 字节，再运行未经修改的仓库评分脚本。

内核在 WSL RISC-V 工具链中编译通过，仓库原有的三组 QEMU 评分用例共 **100/100**。正常内核运行时实际输出十行 `100 ticks` 后通过 SBI 正常关机。额外测试在临时源码副本中触发 16 位非法指令、16 位断点、32 位断点及仅按 2 字节对齐的 32 位非法指令，四种异常均正确返回。未知中断和其他异常的兜底输出也通过原有测试检查。

## 七、OS 原理中重要但本实验未覆盖的知识点

1. **进程管理与抢占式调度。** 时钟中断提供抢占机会，但完整调度还需要进程控制块、就绪队列、调度策略和进程上下文切换。本实验的现场保存不能代替这些机制。
2. **完整的用户态执行与系统调用。** 特权级和 `ecall` 为服务入口提供基础，实际系统还需要用户地址空间、用户栈、系统调用编号分发、参数检查和用户内存访问保护。
3. **缺页处理及按需虚拟内存。** 能识别缺页原因与出错地址，只是处理入口；真正恢复执行还涉及页面分配、映射建立、权限验证、页面置换及后备存储。
4. **多核同步与内存一致性。** 本地屏蔽中断无法解决其他 hart 的并发访问。多核内核还需要自旋锁、内存屏障、原子操作的顺序约束和核间中断机制。
5. **设备 I/O 和驱动框架。** 时钟展示了事件通知方式，完整 I/O 还包括外部中断控制器、设备寄存器、DMA、请求队列，以及进程的等待与唤醒。
6. **复杂中断管理。** 本实验未系统实现中断优先级、受控嵌套、中断下半部和中断负载控制。这些机制用于平衡响应延迟、处理开销和共享状态安全。
7. **高级同步与死锁处理。** 关闭中断只是一种局部保护手段，完整系统还需要互斥锁、信号量、条件变量及死锁预防或检测机制。
8. **高精度时间与定时任务管理。** 固定间隔事件之外，实际系统通常还需要软件定时器队列、超时管理、单调时钟、计时误差补偿和无周期时钟设计。
